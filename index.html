      NOTE 01 · COMPUTE PLATFORM & K8S SCHEDULER 计算平台构建

      计算平台构建笔记：异构算力调度、Virtual Kubelet 与 Fail-Closed 控制面

      沉淀自 Seed-AI4S 与华为南研所实习：如何构建高可靠的大规模 Serverless GPU 计算平台？

      面向科学计算（AI4S）与大规模训练/推理工作负载，计算平台控制面与调度器的核心架构要点：

      • 三级调度队列与两阶段绑定：K8s Scheduler 内部通过 ActiveQ / BackoffQ / UnschedulablePods 管理待调度 Pod；Scheduling 阶段串行执行 Filter → Score → Reserve (Assume) 乐观预占算力，Binding 阶段异步执行，失败时必须触发 Unreserve 精确回滚缓存。
      • 跨平面数据流反转与 Fail-Closed 铁律：内场 Controller 将异构 Spot 配额与共享存储（NAS）权限同步写入 Redis 快照；算力侧 Scheduler 插件纯本地读取快照。一旦 Redis 数据缺失、过期超过容忍窗口或权限不可确认，强制保持 Pod Pending（Fail-Closed），绝不基于猜测容量放行。
      • Virtual Kubelet 多节点池与进程管理（PM）：通过 Virtual Kubelet 将底层集群（如 Merlin / MLP）抽象为 K8s 虚拟节点池；工作负载容器内 PM 采用流式消费与超时自动认领（XAUTOCLAIM）保证控制指令幂等投递。
      // Fail-Closed：快照不可信时一律 Pending，绝不猜测放行
func (p *Plugin) Filter(ctx, pod, node) *Status {
    snap, ok := p.cache.Get(node.Name)
    if !ok || snap.Expired(p.tolerance) {
        return framework.NewStatus(Unschedulable, "snapshot missing/stale")
    }
    return snap.Fits(pod)
}
      NOTE 02 · EMBODIED AI INFRA & DATA PLATFORM 具身智能基建

      具身智能基建笔记：多模态机器人数据飞轮、训练编排与闭环仿真评测

      沉淀自 Seed-Robotics 实习：如何支撑具身大模型（VLA）从真机采集到云端训练与仿真验证的工程闭环？

      具身智能平台相比传统纯文本/单模态 AI Infra，核心挑战在于强异构多模态数据流与物理交互仿真：

      • 端云协同采集与时间戳对齐：机器人本体包含多路 RGB-D 相机、激光雷达、IMU 与高频机械臂关节编码器（频率从 30Hz 到 1000Hz 不等）；数据入湖前必须完成硬件/软件级时间戳对齐、静止/异常 Episode 自动裁剪与统一格式封装（如 MCAP / RLDS / Lance）。
      • 高吞吐流式数据加载（Data Loader）：多视角视频解码极易成为训练瓶颈导致 GPU 空转；平台需结合对象存储（TOS/S3）分片预取、分布式缓存加速与 GPU 硬件解码（NVDEC）提升训练 MFU。
      • 云端并行仿真评测（Sim Eval）：将训练产出的 Checkpoint 自动挂载至容器化 GPU 渲染集群（Isaac Gym / MuJoCo），并发跑百级仿真场景评测成功率，并将失败长尾轨迹回流至训练集形成数据飞轮。
      NOTE 03 · GPU MONITORING & MODEL DEPLOYMENT 算力监控与推理

      GPU 集群监控与图像模型部署：从 TensorRT 量化到万卡级 DCGM/RDMA 遥测

      沉淀自基流科技与科大先研院实习：单卡推理极致加速与大规模智算集群故障感知。

      贯通「单卡模型推理优化」与「集群级硬件/网络监控」的核心技术指标：

      NOTE 04 · SELF-EVOLVING AGENTS Agent 自进化

      Agent 自进化笔记：从在线工具容错到记忆演进与技能库自动合成

      如何让智能体在环境反馈中自主修复故障、提炼长期记忆、合成可复用工具并防止能力退化？

      构建真正具备自进化能力（Self-Evolving）的生产级智能体，需要打通从「单次执行闭环」到「跨会话能力复利」的四层机制：

      • 第一层：执行期在线故障自愈（Online Failure Recovery） — 将外部工具/MCP 调用异常显式建模为 6 类结构化错误（StructuredError：Schema/类型错误、必填上下文缺失、权限/配额拒绝、限流超时、下游服务故障、空结果/语义偏离），由确定性恢复策略（参数自省修正、退避重试、备选工具切换、局部 Re-plan）取代盲目重试。
      • 第二层：轨迹反思与分层记忆演进（Reflexion & Memory Consolidation） — 任务结束后对完整交互轨迹（Trajectory）执行归因反思（Verbal RL / Critique）：将具体排障案例存入情景记忆（Episodic Memory），将跨任务复用的领域事实与排障 SOP 蒸馏进语义与程序性记忆（Semantic & Procedural Playbook）；定期执行记忆去重合并、矛盾消解与陈旧条目剪枝（Dream/Pruning）。
      • 第三层：工具与提示词自演化（Skill Synthesis & Prompt Optimization） — 借鉴 Voyager 与 DSPy / TextGrad 思想，把高频成功的多步工具编排自动抽象封装为原子代码技能（Skill Library），并通过文本梯度自动优化路由 Prompt 与少样本示例。
      • 第四层：防退化评测门禁（Evaluator-Optimizer & Regression Gate） — 严防「错误经验自我强化（Hallucination Amplification）」；任何新合成的 Skill、记忆规则或改写的 Prompt 入库前，必须通过沙箱单测 + 历史失败轨迹回放（Trajectory Replay）+ 黄金评测集（Golden Benchmark）门禁。
      NOTE 05 · E-COMMERCE ORDER & PRICING 商城交易核心

      商城交易笔记（上）：商品 SPU/SKU、计价分摊、订单状态机与分库分表

      从商品建模、购物车算价、拆单分摊到基因法分片与延时关单的全链路业务设计要点。

      设计高可用商城系统时，商品域与交易履约域必须理清的四个核心模型：

      • SPU 与 SKU 领域分离：SPU（Standard Product Unit）承载分类、品牌、图文详情等公共检索属性；SKU（Stock Keeping Unit）由销售规格笛卡尔积生成，独立绑定价格、条码与库存。商详页高并发读采用「本地缓存 Ristretto + Redis + Singleflight 合并回源 + 监听 Binlog 异步失效」。
      • 促销计价引擎与「一分钱尾差」分摊：叠加平台满减、店铺券、品类券与积分抵扣时，按各商品行（OrderItem）的实付金额占比进行分摊：前 $N-1$ 项向下取整到分，第 $N$ 项用总优惠减去前 $N-1$ 项之和兜底，保证子单实付之和严格等于主单实付，杜绝部分退货时超退或少退。
      • 订单有限状态机（FSM）与防并发跃迁：订单正向（待支付 → 已支付 → 待发货 → 已发货 → 已完成）与逆向售后严禁裸写状态更新，必须通过事件驱动状态机并带前置状态乐观锁：UPDATE orders SET status = 'PAID', version = version + 1 WHERE order_id = ? AND status = 'UNPAID'。
      • 基因法订单号与分库分表路由：海量订单按 buyer_id 分库分表时，将 buyer_id 的后 $k$ 位二进制（分片基因）嵌入分布式订单号 order_id 低位；使得「按买家查订单列表」与「按订单号查详情」均能直接路由至同一物理分片，卖家维度查询则通过订阅 Binlog 异构同步至 Elasticsearch。
      NOTE 06 · INVENTORY, SECKILL & LEDGER 库存与资金安全

      商城交易笔记（下）：三层库存防超卖、秒杀削峰、柔性事务与日终对账

      大促瞬时洪峰下如何守住「绝不超卖、绝不资损」两条生命线？

      库存扣减、跨服务分布式事务与支付清结算的工程落地准则：

      • 三层库存模型与预占机制：分离可售库存（Available）、锁定/预占库存（Reserved）与实物库存（Physical）。下单时 Available - N, Reserved + N；支付成功或发货时 Reserved - N, Physical - N；超时未支付自动关单（时间轮或延迟队列触发）时 Reserved - N, Available + N，且扣减流水必须幂等防重放。
      • 秒杀削峰与热点 SKU 库存分桶：网关层令牌桶限流 → 缓存层用 Redis Lua 脚本原子校验用户限购并预扣库存 → 写入 MQ 异步创建订单；针对单 SKU 十万 QPS 的极端热点，将库存拆分为 $K$ 个子桶（如 stock:sku101:bucket_0..9）分散到不同分片，不足时触发桶间调拨或回退。
      • 柔性事务选型（Outbox vs TCC）：支付成功通知履约/积分优先用本地消息表（Transactional Outbox）保证最终一致；下单同时扣减库存、核销优惠券等需强隔离预留资源的环节采用 TCC（Try-Confirm-Cancel），通过事务状态控制表防范空回滚与悬挂。
      • 支付幂等与 T+1 清结算对账：发起支付与退款必须携带全局唯一幂等键（out_trade_no / out_refund_no），异步回调配合主动查单定时任务兜底；每日凌晨拉取渠道对账单与本地支付单/订单做「笔数、金额、状态」三角核对，自动识别长短款并进入差错平账流程。

      NOTE 07 · DECLARATIVE CONTROL PLANE & DISTRIBUTED 控制面与分布式

      为什么优秀的控制器不怕重启、不怕丢事件，且在网络分区与滚动升级时不会产生脑裂？
