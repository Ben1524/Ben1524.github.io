      NOTE 01 · E-COMMERCE ORDER & PRICING 商城交易核心

      商城交易笔记（上）：商品 SPU/SKU、计价分摊、订单状态机与分库分表

      从商品建模、购物车算价、拆单分摊到基因法分片与延时关单的全链路业务设计要点。

      设计高可用商城系统时，商品域与交易履约域必须理清的四个核心模型：

      • SPU 与 SKU 领域分离：SPU（Standard Product Unit，如 iPhone 16）承载分类、品牌、图文详情等公共检索属性；SKU（Stock Keeping Unit，如 256G 黑色）由销售规格笛卡尔积生成，独立绑定价格、条码与库存。商详页高并发读采用「本地缓存 Ristretto + Redis + Singleflight 合并回源 + 监听 Binlog 异步失效」。
      • 促销计价引擎与「一分钱尾差」分摊：叠加平台满减、店铺券、品类券与积分抵扣时，必须将总优惠金额按各商品行（OrderItem）的实付金额占比进行分摊：前 $N-1$ 项向下取整到分，第 $N$ 项用总优惠减去前 $N-1$ 项之和兜底，保证子单实付之和严格等于主单实付，避免部分退货时超退或少退。
      • 订单有限状态机（FSM）与防并发跃迁：订单正向（待支付 → 已支付 → 待发货 → 已发货 → 已完成）与逆向售后（仅退款 / 退货退款）严禁裸写状态更新，必须通过事件驱动状态机并带前置状态乐观锁：UPDATE orders SET status = 'PAID', version = version + 1 WHERE order_id = ? AND status = 'UNPAID'。
      • 基因法订单号与分库分表路由：海量订单按 buyer_id 分库分表时，将 buyer_id 的后 $k$ 位二进制（分片基因）嵌入分布式订单号 order_id 低位；使得「按买家查订单列表」与「按订单号查详情」均能直接计算出同一分片，卖家维度查询则通过订阅 Binlog 异构同步至卖家库或 Elasticsearch。
      NOTE 02 · INVENTORY, SECKILL & LEDGER 库存与资金安全

      商城交易笔记（下）：三层库存防超卖、秒杀削峰、柔性事务与日终对账

      大促瞬时洪峰下如何守住「绝不超卖、绝不资损」两条生命线？

      库存扣减、跨服务分布式事务与支付清结算的工程落地准则：

      • 三层库存模型与预占机制：分离可售库存（Available）、锁定/预占库存（Reserved）与实物库存（Physical）。下单时 Available - N, Reserved + N；支付成功或发货时 Reserved - N, Physical - N；超时未支付自动关单（时间轮或延迟队列触发）时 Reserved - N, Available + N，且扣减流水必须幂等防重放。
      • 秒杀削峰与热点 SKU 库存分桶：前端答题/验证码打散请求 → 网关层令牌桶限流 → 缓存层用 Redis Lua 脚本原子校验用户限购并预扣库存 → 写入 MQ 异步创建订单；针对单 SKU 十万 QPS 的极端热点，将库存拆分为 $K$ 个子桶（如 stock:sku101:bucket_0..9）分散到不同分片，不足时触发桶间调拨或回退。
      • 柔性事务选型（Outbox vs TCC）：长链路下单拒绝同步阻塞的 2PC。支付成功通知履约/积分优先用本地消息表（Transactional Outbox）保证最终一致；下单同时扣减库存、核销优惠券等需强隔离预留资源的环节采用 TCC（Try-Confirm-Cancel），通过事务状态控制表防范空回滚（Try 未执行先收到 Cancel）与悬挂（Cancel 执行后迟到的 Try 才到达）。
      • 支付幂等与 T+1 清结算对账：发起支付与退款必须携带全局唯一幂等键（out_trade_no / out_refund_no），异步回调配合主动查单定时任务兜底；每日凌晨拉取微信/支付宝渠道对账单与本地支付单/订单做「笔数、金额、状态」三角核对，自动识别长款（渠道多收）与短款（平台漏记）并进入差错平账流程。
      NOTE 03 · KUBERNETES SCHEDULER INTERNALS 算力调度

      K8s 调度器内核必懂：队列流转、两阶段提交与异构拓扑

      理解一个 Pod 从进入调度队列到成功绑定节点，中间经历的状态机与并发设计。

      学习与设计自定义调度插件（Scheduler Plugin）时，必须重点关注以下机制：

      • 三级调度队列：ActiveQ（立即可调度）、BackoffQ（指数退避等待）、UnschedulablePods（等待集群事件唤醒，通过 EnqueueExtensions 注册关注的 Pod/Node/Storage 事件精确移出，避免无效调度循环）。
      • 串行调度 + 异步绑定（两阶段）：Scheduling Cycle（PreFilter → Filter → PostFilter → PreScore → Score → Reserve）是串行的，通过 Assume 乐观扣减缓存资源；Binding Cycle（Permit → PreBind → Bind → PostBind）并发异步执行，一旦失败必须触发 Unreserve 回滚缓存状态。
      • 异构算力与 Gang 调度：分布式训练要求 All-or-Nothing 成组调度（利用 Permit 阶段等待最小副本数齐备），同时需结合节点 NUMA、PCIe Switch 与 NVLink 拓扑做亲和性打分。
      NOTE 04 · DECLARATIVE CONTROL PLANE 控制面架构

      声明式控制面铁律：水平触发、乐观并发与优雅选主生命周期

      为什么优秀的控制器不怕重启、不怕丢事件，且在滚动升级时不会产生脑裂？

      编写 Kubernetes Controller、Operator 或 Virtual Kubelet 时必须守住的架构边界：

      • Level-Triggered（水平触发）与幂等性：WorkQueue 只传递对象的 namespace/name 键，不传递事件 diff；Reconcile 每次从本地 Lister 读取最新期望状态与实际状态做对比，即使中间合并了 10 次变更或进程重启，也能收敛到正确终态。
      • 乐观锁与写冲突处理：更新对象时依赖 metadata.resourceVersion；遇到 409 Conflict 时重新读取最新对象并应用变更，切忌用旧缓存盲目覆盖其他控制器的字段。
      • Leader Election 生命周期收敛：OnStartedLeading 运行在独立协程中，所有子工作循环必须绑定本轮选主的 ctx 与 WaitGroup；当租约丢失或收到 SIGTERM 时，确保在释放租约前排空在途写操作。
      NOTE 05 · DISTRIBUTED CONSISTENCY & STORAGE 分布式系统

      分布式系统防坑指南：共识边界、租约陷阱与流式消息幂等

      网络不可靠、时钟会回拨、进程会 GC 停顿——如何用严谨的协议保证数据安全？

      在设计跨节点状态同步、缓存层与异步任务队列时的核心知识清单：

      • Lease 租约不等于绝对互斥：客户端拿到分布式锁后若发生长 GC STW，锁过期被其他节点获取就会出现双主写冲突；存储层必须校验单调递增的 Fencing Token（或 Epoch/Revision）拒绝旧主写入。
      • 缓存与快照的数据流向：高频读取路径（如调度器读取外部配额或元数据）应通过后台异步同步写成带显式版本号与时间戳的本地 Redis 快照，避免在关键链路上发起跨网同步 RPC。
      • At-Least-Once 与消费端幂等：基于 Redis Streams 或 Kafka 的指令投递应假设消息一定可能重复；通过消费者组 + 超时自动认领（XAUTOCLAIM）解决消费者假死，通过状态机前置条件校验保证幂等执行。
      NOTE 06 · GO RUNTIME & PERFORMANCE 语言运行时

      Go 高并发与性能工程：内存逃逸、GC 屏障与并发原语选型

      写出不仅逻辑正确，而且对 CPU Cache 和垃圾回收器友好的系统级 Go 代码。

      深入 Go 运行时内部机制，指导日常代码评审与性能压测：

      • 内存分配与零分配优化：通过 go build -gcflags="-m" 检查逃逸分析；热路径避免接口装箱、闭包捕获大对象与高频切片扩容；合理使用 sync.Pool 复用临时缓冲区（注意放回前重置切片长度并防范池中大对象驻留）。
      • 并发原语与 Context 规范：读多写少且键集合稳定时考量 sync.RWMutex 或分片锁；并发子任务编排优先使用 errgroup.WithContext 并限制最大并发度（SetLimit），严防无界 Goroutine 创建耗尽内存。
      • 性能剖析闭环：CPU 瓶颈看 pprof profile，堆内存暴涨看 inuse_space，GC 压力看 alloc_objects，锁竞争与协程阻塞看 mutex / block 与 go tool trace。
      NOTE 07 · AI INFRA & AGENT SYSTEMS AI 基础设施

      AI Infra 与 Agent 工程：从 GPU 算力底座到智能体容错闭环

      连接底层异构硬件、弹性容器调度与上层大模型推理/工具调用的知识脉络。

      面向 AI4S（科学计算）与大模型训推场景，基础设施工程师需要补齐的跨界认知：

      • 算力、显存与互联瓶颈：区分算力受限（Compute-bound）与访存受限（Memory-bound）；理解机内 NVLink/NVSwitch 与机间 RoCEv2/InfiniBand 网络拓扑对 AllReduce 集合通信的影响。
      • Serverless GPU 冷启动优化：容器镜像按需延迟加载（Lazy Pulling / Nydus / eStargz）、共享只读模型权重卷（高性能并行文件系统 / NAS 预热）与高优抢占池水位控制。
      • Agent 确定性护栏：大模型本身是概率性的，但工具调用层（MCP / Tool Runtime）必须是确定性的——对外部工具错误进行结构化分类（参数错误、鉴权失败、限流超时），结合幂等键与回退策略实现自动恢复。
      NOTE 08 · RESILIENCE & OBSERVABILITY 可靠性工程

      高可靠系统设计准则：Fail-Closed、退避抖动与低基数可观测性

      面向失败设计（Design for Failure）：当一切依赖都可能故障时，系统如何自保？

      把线上复盘沉淀为编码阶段就能机械化检查的架构不变量：

      • Fail-Closed 优先于「猜着跑」：在涉及配额扣减、权限校验、跨租户隔离等安全边界上，一旦上游缓存缺失、过期超过容忍窗口或返回未定义错误，必须显式拒绝或保持挂起（Pending），绝不回退到无限制放行。
      • 防范重试风暴与惊群效应：客户端重试必须设置上限并引入随机抖动（Full Jitter）；大批量定时同步任务避免在同一整点触发，通过哈希打散或滑动窗口平滑流量峰值。
      • 高信噪比可观测性：Prometheus Metric Label 严禁放入用户 ID、任务 ID、Pod 名称等无界高基数（High-Cardinality）字段；高基数上下文一律放入结构化日志（Log）或 Trace Attribute，并将预期内的 Context Cancel 记为 Info 而非 Error。
